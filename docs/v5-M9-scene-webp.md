# v5-M9 · 场景配图换层：体积决策与实测（WebP → AVIF，守 850KB 线）

> 交付物：把已生成的 55 张 800×280 具象配图整合进《心路》，并让 `check-dist-budget` 保持 0 FAIL。
> **最终口径（用户 2026-10-29 拍板）**：**预算线维持 850KB，不第三次抬线**；配图压到 **86.2KB**。
> 本档 §二 同时留档「抬线到 920KB」那条路的完整实测——两条路的数都是实测的，**当前采用 850KB 那条**。
> 逐张语义判定另见 [docs/v5-scenes.md](v5-scenes.md) §三。

## §一、先测量：简报里的三条前提，实测有两条不成立

| # | 简报前提 | 实测 | 结论 |
|---|---|---|---|
| 1 | 当前 dist 基线 **720.36KB** | **761.06KB**（`npm run build` + `check-dist-budget`，31 件产物） | 基线比简报高 40.7KB，余量更小 |
| 2 | （a）按人生阶段**按需加载**可保住预算门、不降画质 | 全量 WebP 入 dist = **1751.82KB FAIL**。本门实现是 `walk(dist/)` 逐文件 gzip 求和——**代码分割/动态 import 不改变这个数值**（拆成 8 个 chunk 仍是同样 52 个文件、同样字节） | （a）在本门语义下**结构上不可行**；它只改善运行时首屏请求，不改善本门指标 |
| 3 | （b）二次压缩到**总量 ≤150KB** 即可通过 | 去掉配图后的基线 = **757.6KB**；757.6 + 150 = **907.6KB > 850KB** | （b）的目标值本身也放不进旧线；真正可用余量只有 **≤92.4KB** |

结论：要守 850KB，55 张（退役后 52 张）必须压进 **~92KB**——这是硬约束，不是偏好。

## §二、方案对比（全部实测，不是估计）

| 方案 | 实测体积 | 画质 | 判定 |
|---|---|---|---|
| 原样 WebP 入 dist | 55 张时 **990.8KB** / 退役后 52 张 **913.3KB** | 无损于源 | ❌ dist 总 1751.82KB（55 张实测），FAIL |
| WebP 800w `-quality 45` | 772KB | 尚可 | ❌ 远超余量 |
| WebP 480w q55 | 374KB | 864px 画幅下明显发虚 | ❌ 既超余量又降分辨率 |
| WebP 400w q20 | 164KB | 不可用 | ❌ 画质与体积双输 |
| AVIF 800×280 均匀 crf50 | 175.7KB | mean SSIM 0.9145 / min 0.7546 | ❌ 超 92KB |
| AVIF 800×280 均匀 crf57 | 102.8KB | mean 0.8739 / **min 0.6616** | ❌ 仍超 92KB |
| AVIF 800×280 逐图 crf45–60 | 131.8KB | **mean 0.8878 / min 0.8199** | ❌ 超 92KB（但画质最好，见 §2.1） |
| **AVIF 800×280 均匀 crf58 + `-still-picture 1`** | **86.2KB**（单张最大 3.0KB） | **mean 0.8672 / min 0.6486** | ✅ **采用**：唯一同时满足「800×280 全分辨率」与「≤92KB」的档位 |

> SSIM 口径：以源 WebP 为参考，`ffmpeg -lavfi ssim`（52 张逐张算，均值/最差写在表里）。
> 编码器：`tools/v5-scenes-encode.mjs`（AVIF / 800×280 / yuv420p / crf58 + `-still-picture 1`）。

**为什么最终选 crf58 这一档**：它是唯一能在 800×280 **不降分辨率**的前提下压进 92KB 的档位。
纪律次序「压缩 > 减帧 > 降分辨率」在这里只剩「压质量档」一条可走；降分辨率（480w/400w）虽然也能进预算，
但在 864px 画幅下反而更糊，是更差的交换。

**代价（如实记录，不粉饰）**：min SSIM **0.6486**（`field-rows` 田野纹理最差，其次 `field-harvest` 0.674、
`outdoors-road` 0.703、`factory-hall` 0.751）。目检结论：**主体可辨**（猫/兔笼/机床排/工人/田垄/工具），
**涂抹集中在渐变与高频纹理区**；375 档图区压到 104px 高时**看不出**，桌面 864px 画幅下**看得出**。
若后续收到「图糊」反馈，正路是 §2.1 的逐图分配且**合计 ≤92KB**（不是直接复用 131.8KB 那张表——它超标）。

### 2.1 未采用方案：逐图 crf45–60（131.8KB，需把线抬到 920KB）

同一批源图另做过一档「质量优先」的分配（`max-min` 贪心：复杂纹理图 crf45–52、平坦图 crf60）：

| 指标 | 均匀 crf58（**采用**） | 逐图 crf45–60（未采用） |
|---|---|---|
| 配图 gzip | **86.2KB** | 131.8KB |
| dist gzip 总量 | **844.03KB**（余量 **5.97KB**） | 889.16KB（需 920KB 线，余量 30.8KB） |
| mean / min SSIM | 0.8672 / **0.6486** | 0.8878 / **0.8199** |
| 桌面 864px 画幅目检 | 渐变区可见涂抹 | 干净 |
| 预算线 | 850KB（不变） | 需 850 → 920KB（第三次抬线） |

**为什么没采用**：用户 2026-10-29 明示**守 850KB、不第三次抬线**——线纪律优先于桌面纹理保真。
两条路的数都在上表，**切回只需改编码器档位并复跑门 + e2e**，不是一次性决定。
遗留风险已登记 [plan/v5/backlog.md](../plan/v5/backlog.md) 观察区（余量仅 5.97KB + 桌面纹理折损）。

## §三、最终落定与实测

- **格式**：AVIF（AV1 帧内），800×280，yuv420p，均匀 crf58 + `-still-picture 1`（见 `tools/v5-scenes-encode.mjs`）。
- **预算线**：**850KB 不变**（前两次抬线 500→650→850 的记录仍有效，本版**不**新增第三次）。
- **结果**：dist gzip **844.03KB / 850KB**（余量 **5.97KB**），`0 FAIL 0 WARN`。

### 顺带修掉的一个隐性浪费

Vite 默认把 <4KB 资源内联成 base64。AVIF 大多 1–3KB，会**整批被塞进 JS 主干**（base64 膨胀 33%，且 `<img>` 失去独立请求）。
实测：全局 `assetsInlineLimit: 0` 会把 250 枚图标 SVG 也拆成独立文件、总量反而涨 40KB（每份多一层 gzip 头）；
因此只对 `.avif` 关闭内联：

```ts
assetsInlineLimit: (filePath) => (filePath.endsWith(".avif") ? false : undefined),
```

## §五、可复现

```bash
node tools/v5-scenes-encode.mjs          # 源 WebP → 分发 AVIF（crf58；需本机 ffmpeg）
node tools/v5-scenes-encode.mjs --check  # 只核验分发物在位与体积
npm run build && node tools/check-dist-budget.mjs
```

源图在 `assets/web-ready/scenes-src/*.webp`（**不参与分发**），退役图在 `assets/web-ready/scenes-src/retired/`。
编码器是**离线素材工具**：产物已入库，他人 clone 后直接构建，不需要装 ffmpeg（K2 零运行时依赖不受影响）。
