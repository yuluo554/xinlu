# v5-M9 · 场景配图换层：体积决策与实测（WebP → AVIF + 第三次抬线）

> 交付物：把 55 张 800×280 具象配图整合进《心路》，并让 `check-dist-budget` 保持 0 FAIL。
> 判据单源：本档 §三/§四（体积与格式）+ [plan/v5/00 §决策记录](../plan/v5/00-README总览.md)（抬线拍板）。
> 逐张语义判定另见 [docs/v5-scenes.md](v5-scenes.md) §三。

## §一、先测量：简报里的三条前提，实测有两条不成立

| # | 简报前提 | 实测 | 结论 |
|---|---|---|---|
| 1 | 当前 dist 基线 **720.36KB** | **761.06KB**（`npm run build` + `check-dist-budget`，31 件产物） | 基线比简报高 40.7KB，余量更小 |
| 2 | （a）按人生阶段**按需加载**可保住预算门、不降画质 | 全量 WebP 入 dist = **1751.82KB FAIL**。本门实现是 `walk(dist/)` 逐文件 gzip 求和——**代码分割/动态 import 不改变这个数值**（拆成 8 个 chunk 仍是同样 55 个文件、同样字节） | （a）在本门语义下**结构上不可行**；它只改善运行时首屏请求，不改善本门指标 |
| 3 | （b）二次压缩到**总量 ≤150KB** 即可通过 | 去掉配图后的基线 = **757.6KB**；757.6 + 150 = **907.6KB > 850KB** | （b）的目标值本身也放不进旧线；真正可用余量只有 **≤92.4KB** |

由此，可行空间只有两个：把 55 张压进 ~92KB（画质代价见 §三），或抬线（§四）。

## §二、方案对比（全部实测，不是估计）

| 方案 | 实测体积（55 张） | 备注 |
|---|---|---|
| 原样 WebP 入 dist（简报默认） | **990.8KB**（WebP 已是压缩格式，gzip 后 ≈ 990KB，几乎不再缩） | dist 总 1751.82KB → FAIL 900KB |
| WebP 800w `-quality 45` | 772KB | 仍远超余量 |
| WebP 480w q55 | 374KB | 仍超；且 480 宽在 864px 画幅上明显发虚 |
| WebP 400w q20 | 164KB | 画质不可用（q20）且仍超 92KB |
| AVIF 800×280 均匀 crf50 | 175.7KB | mean SSIM 0.9145 / min 0.7546 |
| AVIF 800×280 均匀 crf57 | 102.8KB | mean 0.8739 / **min 0.6616**——纹理区（田野/厂房/街道）可见糊化 |
| **AVIF 800×280 逐图 crf45–60（采用）** | **131.6KB**（52 张，退役 3 张后） | **mean SSIM 0.8878 / min 0.8199** |

> SSIM 口径：以源 WebP 为参考，`ffmpeg -lavfi ssim`。逐图分配 = `max-min` 贪心：
> 复杂纹理图（田野/厂房/街口/公园/校门）给 crf45–52，平坦图（黑板/床铺/书桌/电台）给 crf60。

**为什么不是「均匀一档」**：均匀 crf57 能把总量压到 102.8KB，但最差图 0.66、纹理糊成一片；
逐图分配在**更多字节（131.6KB）下把最差图抬到 0.82**，均值也更高——同一条预算线内更划算。

### 2.1 落选方案：均匀 crf58 + cpu-used 6（84.4KB，维持 850KB 线）

同一批源图另有一档实测值得留档，因为它是「不抬线」路线的上限：

| 指标 | 均匀 crf58 / cpu-used 6 | 采用方案（逐图 crf45–60） |
|---|---|---|
| 配图 gzip | **84.4KB**（单张最大 2.7KB） | 131.6KB |
| dist gzip 总量 | 841.8KB（**余量仅 8.2KB**） | 889.2KB（余量 30.8KB） |
| mean / min SSIM | 0.847 / **0.618** | 0.888 / **0.820** |
| 桌面 864px 画幅目检 | 渐变区可见涂抹（田野/厂房/街道最明显） | 干净 |

**为什么落选**：①min SSIM 0.62 意味着最差几张已经是「看得出糊」的程度，而 375 档 104px 高的缩略下看不出来、
桌面 864px 画幅下看得出来——不能拿小屏的观感当全端结论；②余量只有 8.2KB，下一轮任何内容增量（一条事件、
一个字符串常量都是 KB 级）就会把门打红，等于把预算问题推给下一棒。
**但它不是错方案**：如果要严格守 850KB 且接受桌面画质折损，这一档就是可行解——参数与产物留档于此，可随时切回。

## §三、拍板方案：AVIF 逐图档位 + 抬线 850 → 920KB

- **格式**：AVIF（AV1 帧内），800×280，yuv420p，逐图 crf45–60（表见 `tools/v5-scenes-encode.mjs`）。
- **预算线**：**850 → 920KB**（第三次抬线；前两次 500→650→850）。
- **结果**：dist gzip **889.16KB / 920KB**（余量 **30.8KB**），`0 FAIL 0 WARN`。

### 为什么抬线，而不是继续压

1. 配图层是**新增的图片资产层**：v5.0.x 的线稿只有 19.3KB（gzip），55 张具象图在**任何现代格式**下都 ≥100KB 量级——这不是「代码变胖」，是资产类别变化。
2. 要做到旧线 850KB，只能把 55 张压到 ≤92.4KB（约 1.7KB/张），实测 min SSIM 0.769、纹理糊化；这违背本项目「压缩 WebP > 减帧 > 降分辨率」里**最后才降画质**的次序，也违背本次交付的目的（把线稿升级成具象配图）。
3. 抬线幅度 **+70KB**，恰等于配图层实测净成本；抬线后仍留 30.8KB 余量给后续内容增量。
4. **不是靠瘦身解决**，如实记在这里：能瘦的都瘦了（AVIF 逐图档位、`.avif` 关闭 base64 内联、退役 3 张零使用图），剩下的就是图片本身的字节。

### 顺带修掉的一个隐性浪费

Vite 默认把 <4KB 资源内联成 base64。AVIF 大多 1–7KB，会**整批被塞进 JS 主干**（base64 膨胀 33%，且 `loading="lazy"` 失效）。
实测：全局 `assetsInlineLimit: 0` 会把 250 枚图标 SVG 也拆成独立文件、总量反而涨 40KB（每份多一层 gzip 头）；
因此只对 `.avif` 关闭内联：

```ts
assetsInlineLimit: (filePath) => (filePath.endsWith(".avif") ? false : undefined),
```

## §四、最终实测

| 指标 | 改前（v5.0.1） | 改后（v5.1.0） |
|---|---|---|
| 配图层格式 | 内联 SVG 线稿 | AVIF 具象图 `<img>` |
| 配图层图数 | 55 张 / 21 类 | **52 张 / 20 类**（`funeral` 整类退役，见 v5-scenes.md §3.2） |
| 旧线稿 SVG | 分发物（`?raw` 内联） | 移入 `scenes-src/legacy-svg/`，**不作运行时 fallback**（全仓 grep 确认零引用，保留只作画法参照） |
| 配图层字节（dist gzip） | 19.3KB（含在 JS 内） | **131.6KB**（52 个独立文件） |
| dist gzip 总量 | 761.06KB | **889.16KB / 920KB** |
| 预算线 | 850KB | **920KB** |
| 覆盖 | 239/295 = 81.0% | 228/295 = 77.3%（语义订正后主动豁免 33 条错配事件） |
| `check-dist-budget` | 0 FAIL | **0 FAIL / 0 WARN** |

## §五、可复现

```bash
node tools/v5-scenes-encode.mjs          # 源 WebP → 分发 AVIF（逐图 crf；需本机 ffmpeg）
node tools/v5-scenes-encode.mjs --check  # 只核验分发物在位与体积
npm run build && node tools/check-dist-budget.mjs
```

源图在 `assets/web-ready/scenes-src/*.webp`（**不参与分发**），退役图在 `assets/web-ready/scenes-src/retired/`。
编码器是**离线素材工具**：产物已入库，他人 clone 后直接构建，不需要装 ffmpeg（K2 零运行时依赖不受影响）。
